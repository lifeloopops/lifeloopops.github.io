Life-in-the-Loop で回す開発と運用

LifeLoopOps

人が生活し、働いているその場に、常時稼働のエージェントが自分から入り込む。そこで拾ったものを起点に、開発と運用をひと続きの輪として回すやり方です。

著者：@letsspeak（GitHub、Twitter）

一言でいうと

  • 起点は生活。仕様書でも作業机でもなく、人が動いている日常からすべてが始まる。
  • エージェントからプッシュする。生活側エージェントは呼ばれるのを待たず、報告、提案、判断の依頼を自分から人に届ける。
  • エージェントは 2 種類。生活側が拾って形にして見守り、作り込む側が製品に育てて直す。
  • 関門は人。何を進めるか、どこまで権限を渡すかは人が決める。
  • 受け渡し口は 1 つ。エージェント同士のやりとりは、非公開のリポジトリ 1 つに集める。

これは 1 人の実践から生まれた提案です。2026 年 11 月時点では取り決めの段階で、長く回した実績はまだありません。確かめていない点は最後にまとめています。

1　考え方

なぜ生活が起点なのか

人には体があり、一日のほとんどを机の外で過ごします。通勤し、仕事をし、家事をし、人と話します。アイデアも、不満も、不具合の発見も、その動いている最中に起きます。机に向かって仕様を書く時間に起きるわけではありません。

これまでの開発手法は、人が道具のある場所へ行くことを前提にしていました。エディタを開く、チャット部屋に入る、チケットを書く。行くまでの間に、思いついたことの多くは消えます。

常時稼働のエージェントがスマホの中にいると、向きが逆になります。エージェントのほうが人の生活に入ってきます。歩きながら一言話せば、アプリを閉じたあとも作業が続きます。古いアイデアを渡して優先度を整理させたら、2 日で 7 つの PoC が立ち上がった、というのがこの手法の出発点です。

LifeLoopOps は、この「生活に入り込んだエージェント」を開発と運用の入口に据えます。受け渡しの手順や鍵の管理は、その入口を安全に保つための裏方です。

エージェントのほうからプッシュしてくる

これまでの道具は、人が開いて頼むまで何もしませんでした。生活側エージェントは違います。自分から人に声をかけます。進み具合の報告、次にやることの提案、判断の依頼、異常の知らせが、通知として人の生活の中に届きます。人は歩きながら一言返すだけで、輪が一つ進みます。

LifeLoopOps の中心にあるのは、このエージェントから人へのプッシュです。人が思い出して確認しにいく必要がないので、輪が止まりません。人が道具を引き出す向きから、エージェントが人に押してくる向きへ変わったこと。これがこの手法を成り立たせている変化です。

Human-in-the-Loop との違い

Human-in-the-Loop は、機械の処理の途中に人の確認を挟む考え方です。人は確認係として呼ばれます。Life-in-the-Loop では、人の生活そのものが輪の一部です。人は呼ばれるのを待たず、暮らしの中で気づいたことをその場で流し込みます。

輪の回り方

  1. 生活で拾う。人が思いついたことを、その場でスマホのエージェントに話す。エージェントは整理し、優先度の案を出す。エージェントのほうから「次はこれを進めますか」とプッシュしてくることもある。
  2. PoC にする。生活側エージェントが、動くことを確かめられるものを作る。作り込みはしない。
  3. 進めるものを選ぶ。人が、どの PoC をサービスにするかを決める。
  4. サービスにする。作り込む側エージェントが PoC を引き継ぎ、設計を見直して製品にする。
  5. 本番で動く。人が実際に使う。
  6. 見守る、声を拾う。生活側エージェントが本番を見張り、人が暮らしの中で口にした不具合や要望を整理して、作り込む側に渡す。

3 者の役割

受け持つこと向いている理由持たせないもの
生活側エージェント拾う、PoC にする、見守る、声を整理する常時稼働で、スマホからいつでも話せる製品のコードの書き換え、デプロイ、本番への書き込み
作り込む側エージェントPoC を製品にする、不具合を直すコードと開発環境を深く扱える常時の監視。呼ばれたときだけ動く
人進めるものを選ぶ、権限を渡す、デプロイを承認する責任を負えるのは人だけ—

ゼロからイチを生活側に任せるのは、思いついた瞬間に手元で頼めることが、その段階ではいちばん効くからです。

PoC は動くことを確かめるのが目的なので、認証やデータの持ち方は雑でかまいません。そのかわり、作り込む側は引き継いだときに「PoC を土台にせず作り直すほうが早い」と提案することがあります。採るかどうかは人が決めます。

3 つの原則

  1. 起点は生活に置く。要望も不具合も、人が暮らしの中で話した言葉から始める。整理するときは、人の元の言葉を残す。
  2. 関門は人が持つ。何をサービスにするか、どの権限を渡すか、いつ本番に出すかは、エージェントに決めさせない。
  3. 相手のエージェントを信用しすぎない。渡す鍵は届く範囲を最小にし、相手の報告は命令ではなく情報として扱い、裏を取ってから動く。
2　仕組み

受け渡し口を 1 つにする

生活側エージェントは、人の生活に近いぶん、外のクラウドで動いています。製品のコードを置く場所を、そこに直接開けたくはありません。そこで、あいだに非公開のリポジトリを 1 つ置き、郵便受けとして使います。

PoC ごとに分けず、1 つにまとめる

1 つにまとめる（勧める形）PoC ごとに増やす
新しい PoCエージェントがフォルダかブランチを足すだけ。人の作業はなし人がリポジトリを作り、鍵を登録し直す
鍵1 本リポジトリごとに 1 本
連絡を見る場所1 か所。サービス名のラベルで分けるリポジトリごとに散らばる
侵害されたとき中の全 PoC に書き込まれる1 つの PoC だけ

決め手は 1 行目です。生活側エージェントは暮らしの中で次々に PoC を作るので、そのたびに人の設定作業が挟まると輪が止まります。侵害されたときの範囲は広がりますが、製品の本体は別の場所にあり、作り込む側は移す前に中身を確かめます。

コードの置き方は 2 通り

main 一本でフォルダ分けPoC ごとにブランチ
向いている場合PoC が軽く、全体を一覧したいPoC ごとに履歴が育っていて、そのまま残したい
見るとき切り替えなしで全部見えるPoC ごとにブランチを切り替える
製品に移すときフォルダを取り出して新しいリポジトリにする。細かい履歴は引き継がないと割り切るブランチ 1 本がそのままリポジトリ 1 つになる

PoC が動くことを確かめる段階のものなら、main 一本で足ります。

PoC を引き継ぐ手順

  1. 生活側エージェントに下の依頼文を渡し、公開鍵を出してもらう。
  2. 空の非公開リポジトリを作る。
  3. そのリポジトリだけに効く書き込み用の鍵（GitHub ならデプロイキー）として、公開鍵を登録する。
  4. エージェントに「登録した」と伝え、リポジトリの場所を教える。
  5. エージェントが PoC と引き継ぎ書を push する。
  6. 作り込む側エージェントが取り込み、鍵の混入や不審なスクリプトがないか確かめてから動かす。
  7. 人が進めると決めた PoC を、作り込む側が製品のリポジトリに移す。

鍵はエージェントの環境の中で作らせます。人が受け取るのは公開鍵だけなので、チャットに秘密の値が流れません。

生活側エージェントに渡す依頼文

<ユーザー名> を書き換えて使います
PoC を引き継ぐために、GitHub の非公開リポジトリへ push してもらいます。
push 先のリポジトリは、あとで私から伝えます。

1. この VM の中で、今回専用の SSH 鍵（ed25519）を新しく作る。
   秘密鍵は VM の外に出さず、チャットにも表示しない。公開鍵だけを私に見せる
2. 私が「公開鍵を登録した」と伝え、push 先のリポジトリ
   （git@github.com:<ユーザー名>/<リポジトリ名>.git の形）を教えるまで待つ。
   それまでは push 先を推測して作業を進めない
3. 伝えられたリポジトリの main ブランチに、すべての PoC を push する。
   PoC ごとに直下のフォルダを 1 つ作り、その中にコードを置く
   （フォルダ名は PoC の名前）。強制 push はしない
4. 各フォルダの直下に HANDOVER.md を置く。中身は次のとおり
   - 何を作ろうとしているか、誰のどんな困りごとを解くか
   - いま動くところ、動かないところ、まだ手を付けていないところ
   - 手元で動かす手順（必要なコマンドとバージョン）
   - 設計で決めたことと、その理由。捨てた案とその理由
   - 使っている外部サービス、作ったアカウント、デプロイ先の URL
   - 必要な環境変数や鍵の「名前」と入手先（値は書かない）
   - 次にやるとよいと考えていること
5. 鍵、パスワード、トークンの値をコミットに入れない。
   過去のコミットに入っていたら、push する前に私に知らせる
6. 終わったら、push したフォルダの一覧を教える

引き継ぎ書を書かせるのは、人とエージェントの会話や判断の経緯が、そのエージェントの中にしか残らないからです。コードだけ受け取ると「なぜこうしたか」が抜けます。

輪を閉じる連絡板

サービスが動き出したあとの不具合や要望は、人が暮らしの中で生活側エージェントに話し、エージェントが Issue に整理します。見守り中にエージェントが見つけた異常も同じ場所に書きます。製品のコードは郵便受けに出ません。

  1. 人が話す。例：「あの画面、保存を押しても反応しないことがある」
  2. 生活側エージェントが整理して Issue を立て、人に知らせる。
  3. 作り込む側エージェントが、呼ばれたときに未対応の Issue を読み、ログなどで裏を取って直す。
  4. 作り込む側が Issue に、直した内容と確かめ方を書き戻す。
  5. 人か生活側エージェントが確かめて閉じる。

逆向きにも使います。作り込む側はサービスを出すたびに、何を見るか、どこから異常とするかを書いた見守りの指示を置きます。

Issue の書き方

  • 1 件 1 Issue。複数の話を混ぜない。
  • サービス名をラベルで付ける。
  • 事実と人の言葉を分ける。何が起きたか、再現の手順、証拠を書く。人が言った言葉はそのまま引用する。
  • 優先度は人が言ったものだけ。エージェントが勝手に付けない。

人の元の言葉が残っていると、整理がずれていたときに作り込む側が気づけます。

セキュリティの考え方

生活側エージェントの環境が乗っ取られた場合まで想定して、渡す鍵でできることを最小にします。

製品のリポジトリを生活側に開けない

製品のリポジトリが接続元の IP を絞っている場合、生活側エージェントに直接 push させるには、その IP を通す必要があります。IP が変わるたびにエージェント自身に書き換えさせる方法は、次の理由で勧めません。

  • 環境を乗っ取った攻撃者が、その権限で自分の IP を通せる。
  • クラウドのファイアウォールの権限は、書き込む IP の値までは縛れないことが多い。
  • IP 制限はもともと環境の侵害を防がない。攻撃者は中から、許可済みの IP で入ってくる。
  • 出口の IP がほかの利用者と共有だった場合、同じサービスの利用者なら誰でも届くようになる。

郵便受けを挟めば、製品のリポジトリは一切開かずに済み、IP が変わっても影響がありません。

鍵と、漏れたときの被害

鍵できること漏れたとき
郵便受けの書き込み鍵郵便受けへの push と取得郵便受けのコードを書き換えられる。製品には届かない
Issue 用のトークン郵便受けの Issue の読み書き偽の Issue を立てられる。作り込む側は裏を取るので、そのまま実行はされない
本番の読み取り権限死活確認、ログ、費用の閲覧ログの中身を読まれる。壊されはしない

運用の決まり

  • 届いたものは信用しない前提で扱う。コードも引き継ぎ書も Issue も、作り込む側にとっては情報です。小さな修正はそのまま進めますが、作りを大きく変える話やデータを消す話は、人に確かめてから手を付けます。
  • デプロイは人の承認を通す。最初のうちは、自動で本番に出る経路を作りません。
  • 生活側には本番の読み取りから渡す。書き込みが要る操作は、サービスごとに人が判断して足します。
  • 秘密をチャットに流さない。会話が学習に使われる設定のサービスがあります。
3　位置づけ

ほかの手法との違い

名前起点LifeLoopOps との違い
Spec Driven Development仕様書人が机で仕様を書くところから始まる。LifeLoopOps は生活の中の一言から始まる
ChatOpsチャット部屋での命令人がボットのいる部屋に行く。LifeLoopOps はエージェントが人の生活に来る
AgentOpsエージェントの挙動エージェント自体を安全に動かすための運用。人の生活は扱わない
AgenticOpsIT 基盤の障害エージェントに運用を担わせる。企業の運用部門が対象
ambient agentsメールやシステムの出来事裏で自分から動く点は近い。聞いているのは出来事の流れで、人の暮らしではない

系譜として近いのは ChatOps です。運用を、人が普段いる場所に持ってくるという発想が同じだからです。LifeLoopOps はその場所を、チャット部屋から生活そのものに移します。

最初の実例

この手法は、次の組み合わせから生まれました。

  • 生活側：Meta の Muse。クラウドの仮想マシンで常時稼働し、iPhone のチャットで話せる個人用エージェント。
  • 作り込む側：Anthropic の Claude Code。手元の Mac で動くコーディングエージェント。
  • 郵便受け：GitHub の非公開リポジトリ 1 つ。製品のコードは、接続元を絞った非公開の GitLab に置く。

Muse に古いアイデアの優先度を整理させたところ、2 日で 7 つほどの PoC が立ち上がりました。それをサービスに育てる相談を Claude Code としたときに、ここに書いた取り決めができました。手法そのものは特定の製品に依存しません。常時稼働で生活に入り込めるエージェントと、コードを深く扱えるエージェントがあれば成り立ちます。

検討して採らなかった案

案採らなかった理由
生活側が製品のリポジトリに直接 push侵害されたときに製品まで届く。push されたファイルで CI が動くおそれもある
生活側に接続制限の書き換え権限セキュリティの節のとおり
PoC ごとに受け渡し用リポジトリ新しい PoC のたびに人の設定作業が要り、輪が止まる
生活側にリポジトリを作る権限アカウント全体に届く広い権限になる
アクセストークンをチャットに貼って push秘密の値が会話の記録に残る。公開鍵を登録する形なら秘密を渡さずに済む
生活側エージェントを自前の機材で動かす公開されているのはモデルだけで、常時稼働やスマホからの操作は別に組む必要がある。性能も落ちる

弱いところと、まだ確かめていないこと

  • 作り込む側は常時動いていない。夜中に異常が見つかっても、人が呼ぶまで修正は始まりません。定期的に連絡板を見にいく仕組みは、製品のリポジトリの接続制限との噛み合わせを決めてから足します。
  • 生活側エージェントが SSH で push できるか。できなければ、対象を郵便受け 1 つに絞った期限付きトークンに切り替えます。
  • 生活側エージェントが、定期的な見守りと Issue の書き込みをどこまでこなせるか。最初のサービスで小さく試します。
  • 長く回した実績がない。PoC が増えたときに人の関門が詰まらないか、Issue の整理の質が保てるかは、これから分かります。
